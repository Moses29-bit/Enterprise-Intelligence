# VANTIQ Security Guide — Phase 2 Compatibility Status

## Legacy PHP security behavior

The inspected PHP backend uses `password_hash()` / `password_verify()`, server-side sessions in HttpOnly cookies, CSRF tokens on state-changing requests, server-side login throttling, login history, role/permission checks, and tenant-scoped repository queries. Password reset tokens are stored as hashes and are expiring/single-use. These protections are the compatibility baseline; removing the PHP service before equivalent Java behavior is implemented and tested would reduce security.

## Java status — foundation only, not production-ready

Implemented in the current Spring foundation:

- `LegacyPhpPasswordEncoder` recognizes PHP bcrypt `$2y$` hashes by verifying their `$2a$`-compatible representation. The unit test exercises this prefix conversion with an in-memory generated bcrypt hash; it is not an independently PHP-generated interoperability fixture. Password migration should be opportunistic after a successful login; existing hashes and users must not be reset.
- The encoder does not yet verify non-bcrypt PHP hash formats. Inventory hash algorithm prefixes from the source without exporting/logging hash values; add compatible verification before cutover if any other schemes are found.
- `SecurityConfig` is stateless, permits health/OpenAPI paths, requires authentication for other requests, emits the shared JSON error envelope, and restricts CORS to configured exact origins.
- `TenantAccessGuard` rejects unequal/non-positive organisation identifiers. This is a helper only, not an endpoint/repository boundary.
- `HealthController` returns database health without logging connection details.

Not implemented or not proven:

- No Java login/register/logout/me/password-reset endpoints, JWT access-token authentication filter, refresh-token persistence/rotation/revocation, or token issuance are present. JJWT dependencies and configuration values do not constitute an authentication implementation.
- CSRF is disabled for the intended bearer-token design, but the frontend still uses credentialed session cookies and CSRF headers. Do not enable a cookie-based Java bridge without CSRF protection; do not switch the frontend to bearer tokens until the Java lifecycle exists.
- No Java database-backed login throttling, login history, password-reset delivery, account-status enforcement, role/permission lookup, audit events, or tenant-scoped business repositories are implemented.
- No cross-tenant API/repository test exists. The guard unit test verifies only a helper; it does not prove access isolation.
- Production security properties and CORS must be exercised against a real deployment before release.

## Required implementation controls

- Load `JWT_SECRET`, `DATABASE_URL`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD` only from deployment environment/secrets. Fail closed if JWT configuration is absent once JWT authentication is added.
- Keep Neon JDBC TLS enabled (`sslmode=require`, or the provider’s required pooled/direct URL options).
- Use exact approved origins. Never allow wildcard origins with credentials.
- Enforce organisation scope and permission checks in server-side services/repositories, not client-supplied organisation IDs.
- Persist only hashes of refresh/reset tokens; rotate and revoke refresh tokens; return anti-enumeration responses for password reset.
- Preserve the existing PHP hash format and upgrade the hash after successful legacy verification without logging it.
- Restrict upload size/type, protect state-changing actions from CSRF when cookie-authenticated, and retain secure/HttpOnly/SameSite cookie settings if sessions are retained.
- Do not log passwords, password hashes, bearer/refresh/reset tokens, database URLs, credentials, or raw financial payloads. Return generic client errors with a correlation/reference ID.

## Verification state

Legacy behavior was inspected in PHP source. `mvn -B test` passed five tests, including the bcrypt-prefix and tenant-helper unit tests. The previous stored bcrypt test pair did not verify in the local PHP runtime and was replaced with a generated prefix-conversion case. Confirm compatibility with a non-personal hash generated by PHP before claiming full PHP-to-Java hash interoperability. The tenant test is not an endpoint-level isolation test. Authentication, authorization, CSRF, throttling, refresh lifecycle, and tenant isolation are **not production-verified**.

## Required implementation sequence and acceptance tests

1. Implement authentication against the existing user/role/permission schema. Verify legacy PHP bcrypt hashes without logging them; after successful login, rehash opportunistically only if the stored scheme or work factor needs upgrading. Preserve all user records and never reset passwords as a migration shortcut.
2. Keep the existing PHP session + HttpOnly cookie + CSRF flow active until a Java replacement is complete. If choosing sessions, persist/revoke sessions and retain CSRF protection. If choosing access/refresh tokens, add short-lived access tokens, hashed refresh-token persistence, rotation, reuse detection, logout/revocation, and cookie/CSRF decisions before changing the frontend.
3. Implement password reset with hashed, expiring, single-use tokens and an anti-enumeration response. Add persistent throttling and login history before enabling Java login.
4. Resolve roles and permissions server-side, enforce account status, and derive the active organisation from authenticated server-side identity—not a request body or query string.
5. Add organisation-scoped repositories/services and tenant-aware foreign-key checks. Apply tenant checks to reads, writes, nested resource IDs, exports, imports, and administrative endpoints.
6. Add Spring integration tests for unauthenticated access to protected routes, authorized access, forbidden role/permission access, account suspension, CSRF behavior if cookies are used, token/session revocation, and cross-tenant access through actual HTTP endpoints backed by test repositories/database. Include cross-tenant attempts for both parent and child resource IDs; assert no data is returned or mutated.
7. Run tests against PostgreSQL/Flyway on a disposable instance, then repeat security tests with two organisations and representative roles. Unit-testing `TenantAccessGuard` alone is not an acceptance test.

The current Spring application has no Java auth or business endpoints to test end-to-end. Therefore these endpoint-level tests remain blocked until the corresponding protected endpoint slice exists; do not create placeholder controllers or treat a secured 404 as proof of tenant isolation.
